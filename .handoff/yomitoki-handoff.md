## 2. 書き方の決まり（オーナーの指示、2026年10月12日）
1. エモーショナルに書く。場面と、本人たちの言葉で読ませる物語にする。ただし、きつい言い方はしない。
   - 使わない言い方の例：「はっきり書いておく」
   - 言い切りすぎない。例：「この場面は〜を暗示していたのかもしれない」
2. 書き出しと結びを対にする。
   - 1本目は「僕の判断だ」で始まり、「今度はチームが『これが私たちの判断だ』と胸を張れるかどうか」で終わる。
3. 締めの章では、編集部の考えをはっきり示す。
   - 見出しに「見解」「F1 Grid Walk の見解」「（仮説）」は付けない。中身を表す普通の見出しにする（例：「6位が残したもの」）。
   - 見出しで、章の最後の一文を先に言ってしまわない。
4. 根拠は報道で裏づけられることだけにする。
   - 根拠のない「〜できた可能性もあった」は書かない。
   - 推測を書くときは「これは推測だ」と分かるように書く。
5. 本文に「F1 Grid Walk としては」「F1 Grid Walk の推測で」などと書かない。
6. 出典は本文に挟まない。記事の最後に、媒体名・記事タイトル・リンクを並べる。
7. 「3つの報道から」「確認した3本」など、何本の記事から作ったかを本文に書かない。世界の報道をまとめた F1 Grid Walk の記事として書く。
8. 人の気持ちを、報道にない形で決めつけない。
   - ×「エンジニアの返事は短かった」 → ○「エンジニアは『了解、ありがとうルイス』と返した」
9. 分からない人がいるたとえは使わない（例：小田原評定）。
10. 実現しない願いで締めない（例：「いつかフェラーリから聞いてみたい」）。
11. 次のレースの章では、オーナーの考えを大事にする。
    - 「結果が出なくても、一貫した筋の通った判断なら、チームもドライバーもファンも納得できる」
12. 長さは約2,000〜2,500字。章は6〜7つで、それぞれに見出しを付ける。

## 3. 事実確認のルール
- 使う報道の原文は、すべて開いて読む。数字・発言・順番は原文と照らし合わせる。
- 開けなかった原文の内容は使わない。
  - 転載（Yahoo Sports など）で読んだときは、出典にそう書く。
- 引用の訳は意味を変えない。語気（怒っていた、冷たかった など）を足さない。
- 公式資料の数字（ピットロスなど）は、formula1.com などの出どころを出典に入れる。
- 迷ったら書かない。

## 4. 作り方（技術）
- リポジトリは F1GridWalk/f1gridwalk.github.io です。main がそのまま公開サイトになります。
- 読み解きは topics/<slug>.json を1つ作ります。build.py がページを作り、トップにも自動で出します。
- JSON の形は、1本目の JSON をそのまま手本にしてください。主な項目は次の通りです。
  - 基本：slug, gp, title, sub（"F1 Grid Walk の読み解き"）, dek（事件の短い説明、2文）, checked（確認日）, checkedNote（確認した範囲）
  - story：
    - title："F1 Grid Walk の読み解き"
    - by："F1 Grid Walk 編集部"
    - hook：記事の書き出しの一言（例："チェッカーフラッグのあと、ハミルトンは無線でこう言った。「ごめん、みんな」"）。
      - トップページで、見出しの下に出る。
      - 本文の最初の場面からそのまま取り、読みたくなる一言にする。
      - 字数や読む時間は、どこにも出さない（オーナーの判断）。
    - body：[["h","見出し"],["p","段落"],…]
    - sources：[{"name","title","url","links":[{"label","url"}],"note"}]
    - terms：[["本文の言葉","用語辞典のid"],…]
      - 本文の言葉とルールブック（deep/rules.json）の用語を結びつける。
      - 辞典の見出し語と書き方が違う言葉に使う。
      - 例：["ピットロス","pit-loss"], ["コースに残る","stay-out"], ["順位を入れ替えなかった","team-orders"], ["無線","team-radio"], ["ソフト","tyre-compounds"]
      - 見出し語どおりの言葉（バーチャルセーフティカー など）は自動でつながる。
      - つながった用語は、本文で点線の下線になり、タップすると説明が出る。記事の最後の「この記事に出てくる用語」にも並ぶ。
      - 記事の中心になる用語（その回の戦略やルール）は、必ずつなぐ。id は deep/rules.json に実在するものだけを使う。
  - preview：[{"lens":"決勝プレビューのslug","h2":"答える注目点の見出し（そのまま）","added":"YYYY-MM-DD"}]
    - その読み解きが、レース前のコラム（決勝プレビューなど）で挙げた注目点の「答え合わせ」になっているときに書く。
    - 書くと、プレビューの該当の注目点の下に「決勝のあとで（追記）／この注目点は、どうなった？」の囲みが出る。読み解きの側には「決勝前は、こう見ていた」が出る。
    - 当てはまる注目点がなければ書かない。無理につながない。
  - 記事の後ろに並ぶ材料：common, outlets（id, angle, adds, note, links）, sourceItems, diffs, unknownsFillable, unknownsLimits, decision, next（q, rules：用語辞典のid）, todo, updates
  - outlets の id は、news/archive.json に実際にある記事の id にする。
- 書いている途中は "draft": true を付けます。
  - PREVIEW_DRAFTS=1 python3 build.py で、下書きも含めて作れます。
  - 公開するときは draft を外します。
- topics/*.json は、ニュース係（定時の更新）には触らせない決まりです。読み解きデスクだけが書きます。

## 5. 公開までの流れ（必ず守る）
1. main から preview-<名前> ブランチを作り、そこで作業して push する。
2. スマホ幅（390px）で、ライトとダークのスクリーンショットを撮ってオーナーに送る。
   - ローカルの python3 -m http.server と Playwright を使う。
3. オーナーの「OK」（オーケー、オッケーも可）をもらう前に、main は絶対に変えない。
4. OK が出たら、次の順で進める。
   - main を最新にしてから、ブランチを --no-ff でマージする。
   - build.py を実行し、__pycache__ を消して、commit・push する。
   - GitHub Actions の結果が success になったか確かめる。
5. 直しの指示が来たら、小さな直しでも同じ流れ（プレビュー → OK → 公開）で進める。
